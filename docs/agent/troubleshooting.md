# エラー code と対処

devhub の API エラーは次の形で返る。

```json
{"error": "…", "code": "…", "hint": "…"}
```

分岐には **`code` を使う**。`error` は人間向けの文言で、予告なく書き換わる。
`code` が付かないエラー（各ツールの個別エラー）もあり、その場合は `error` を読む。

## 認証・接続

### `missing_token` — 401

`/api/...` をトークンなしで叩いた。トークンは devhub が自分のページに埋め込むもので、
ブラウザ以外は入手できない。

**対処**: 同じパスを `/ai-api/...` に置き換える。`/api/ports` → `/ai-api/ports`。
詳細は [`agent/ai-api`](ai-api.md)。

### `missing_agent_token` — 401

`/ai-api/...` に same-user agent token がないか、値が一致しなかった。

**対処**: `$DEVHUB_HOME/settings/ai-api-token`（既定
`~/.devhub/settings/ai-api-token`）を読み、`X-Devhub-Agent-Token` ヘッダで送る。
このファイルは同じ OS ユーザーだけが読める権限で作られる。

### `not_loopback` — 403

同じマシン以外から接続した。devhub は 127.0.0.1 にしか bind せず、ネットワーク越しには
到達できない。

**対処**: devhub が動いているホスト上でクライアントを実行する。

### `cross_site` — 403

`Sec-Fetch-Site` ヘッダが付いていた。ブラウザからのクロスサイトリクエストに見えるため
弾かれた（ユーザーが開いている外部サイトが 127.0.0.1 を fetch する攻撃を防ぐ）。

**対処**: `Sec-Fetch-Site` を送らないクライアント（curl、各言語の HTTP クライアント）から叩く。
ヘッダを手で付けている場合は外す。

### `host_not_allowed` — 403

Host ヘッダが `localhost` / `127.0.0.1` のどちらでもなかった。

**対処**: `http://localhost:<port>` か `http://127.0.0.1:<port>` を使う。
ポートが分からなければ `devhub status`。

## 承認

`/ai-api` の書き込みは、ダッシュボード上でユーザーが承認するまでブロックする。
**エージェント単独では書き込みを完了できない。**

### `approval_rejected` — 403

ユーザーが明示的に拒否した。

**対処**: **再試行しない。** 同じ要求を投げ直すのは、断られた依頼を繰り返すのと同じ。
何をしたかったのかをユーザーに説明し、意図を確認する。

### `approval_timeout` — 408

60 秒待って誰も応答しなかった。ユーザーがダッシュボードを見ていなかった可能性が高い。

**対処**:

1. ユーザーに「devhub のダッシュボード（`http://localhost:<port>`）を開いて、
   承認プロンプトが出たら押してほしい」と依頼する
2. **リクエストを投げ直す**

タイムアウトしたリクエストは承認待ち一覧から**既に消えている**ので、
投げ直さない限りユーザーが押せるものは存在しない。ここを間違えると、
存在しないプロンプトをユーザーに探させることになる。

同じ操作を繰り返すなら、ユーザーに承認時の「常に許可」を勧めてもよい。
ただし「常に許可」はクエリ文字列まで含めて一致したときだけ効く。
`GET /ai-api/open?path=/a` を許可しても `?path=/b` は再度確認される —— 一度の許可で
任意のディレクトリが開けるようになってはいけないため。

## 経路そのものが存在しない

### `no_ai_api_route` — 403

そのルートは `/ai-api` からは意図的に使えない。承認を待っても通らないので、
**再試行しても意味がない**。

| ルート | 理由 |
|---|---|
| `POST /ai-api/logs/clear` | エージェントが自分の活動記録を消せてはならない |
| `POST /ai-api/logs/archive` | 何を残すかはユーザーが決めること |

**対処**: それが本当に必要ならユーザーにダッシュボードから実行してもらう。
ログを**読む**だけなら `GET /ai-api/logs` が承認なしで通るので、
自分の失敗を調べる用途はそちらで足りる。

### `/ai-api/approval/*` — 404（`code` は付かない）

承認 API は `/ai-api` に**存在しない**。自分の要求を自分で承認できる経路が
あってはならないので、封鎖しているのではなく最初から生えていない。
上の `no_ai_api_route` とは別物で、返るのは 403 ではなく 404。

**対処**: 承認はユーザーがダッシュボードで行う。エージェント側からは
`http://localhost:<port>/` を開いて押してもらうよう頼む以外にできることはない。

## 診断の順序

どこで詰まっているか分からないときは、上から確認する。

```bash
devhub status                              # 起動しているか（非稼働なら exit 1）
TOKEN=$(cat "${DEVHUB_HOME:-$HOME/.devhub}/settings/ai-api-token")
curl -s -H "X-Devhub-Agent-Token: $TOKEN" http://localhost:8765/ai-api/info
devhub doctor                              # どの devhub が動いているか
```

`devhub status` が落ちるならサーバーが動いていない。ユーザーに `devhub start` を
依頼する（エージェントがフォアグラウンドのサーバーを起動すると、そのまま張り付いてしまう）。

`doctor` は「PATH 上のどの devhub が起動対象か」「実際に動いているのはどれか」を出す。
複数の devhub を入れている環境で、変更したはずの挙動が反映されないときに効く。

## ドキュメントを探す

```bash
devhub docs list             # 一覧（name と description）
devhub docs show <name>      # 本文
```

HTTP からも読める: `GET /ai-api/docs`、`GET /ai-api/docs/<name>`。
