# 0004. コンポーネントの状態モデル（ポート近似と unknown）

- **Status**: Accepted (2026-08-04)
- **対象ツール**: env-launcher
- **関連**: 計画 `devhub-env-launcher-runtime-plan.md` §3.4 / §5 / §13、docs/env-launcher/0002（stop は宣言 spec からの推測で kill する）

## Context（背景）

シナリオ切替は「今動いているもの」と「動かしたいもの」の差分で決まる。したがって
**現在状態をどれだけ正確に知れるか**が、そのまま「何を勝手に止めてよいか」の限界になる。

env-launcher が扱う 2 種類の component は、状態の分かり方がまるで違う。

- `host_process`: devhub はターミナルにコマンドを渡すだけで、実際のプロセスは
  ユーザーのシェルの子になる。PID は追えず、**宣言ポートの LISTEN の有無でしか
  推測できない**。ポートを宣言していないプロセスは何も分からない。
- `compose_service`: `compose ps` が service 単位の状態を返す。ただし daemon が
  落ちていれば「止まっている」のか「見えないだけ」なのか区別できない。

素朴に「分からない ＝ 停止中」と扱うと、切替のたびに devhub が

- 動いているプロセスを二重起動する、あるいは
- **ユーザーの他の作業（無関係な同名ポートの常駐プロセス等）を kill する**

ことになる。後者は取り返しがつかない。

## Decision（決定）

**状態は running / stopped / unknown の 3 値とし、unknown は自動停止の対象にしない。**

- `host_process` の running は **ポート LISTEN による近似**である。ポート未宣言なら
  unknown（「監視できるポートが宣言されていません」）。
- `compose_service` の状態取得に失敗したら unknown とし、**Docker / Colima 自身の
  エラーメッセージをそのまま理由として表示する**。devhub が言い換えると
  「バイナリが無い」と「daemon が落ちている」の区別が消える。
- unknown の component は
  - 目的状態に**含まれる**なら起動する（含めないと目的状態を満たせないため）。
    ただし「既に起動していれば重複する」と警告する。
  - 目的状態に**含まれない**場合も**停止しない**。代わりに「自動停止の対象に
    しません」と警告する。
- 確実な状態取得と停止が要るものは `compose_service` として定義する、という
  逃げ道を用意する。これがコンテナ系を第一級で入れた理由でもある。
- plan と apply の間で状態が変わった場合に備え、plan は観測状態の fingerprint
  （component→state のソート済みペアの sha256 先頭 16 桁）を持ち、apply 時に
  一致しなければ 409 で拒否する。**ユーザーが確認した「止まるもの」と実際に
  止まるものがずれない**ことが目的で、単なる楽観ロックではない。

## Consequences（結果）

### 正
- devhub が把握していないプロセスを勝手に殺すことがない。
- 「なぜ unknown なのか」が常に理由付きで出るので、ユーザーは
  「ポートを宣言する」「compose_service にする」「daemon を起動する」の
  どれを直せばよいか分かる。
- 状態取得の失敗が切替全体を止めない。host_process だけの環境は Docker が
  無くても従来どおり動く。

### 負・制約
- 同じポートを別の何かが LISTEN していれば running と誤認する。ポート近似の
  限界であり、PID を追えない以上この ADR では解消しない。
- 同一シナリオの再適用は host_process については冪等にならない場合がある
  （ポート未宣言なら毎回起動される）。
- unknown が多い環境では警告が増える。黙って正しく振る舞えない以上、
  黙らないほうを選んだ。

## 代替案

- **PID を追跡する**: ターミナル起動をやめてサブプロセスとして持つ必要があり、
  「ユーザーのシェルでコマンドを動かす」という env-launcher の前提を壊す。
- **unknown を stopped 扱いにする**: 差分計算は単純になるが、上記の
  「無関係なプロセスを kill する」事故を招く。状態モデルの単純さと引き換えに
  破壊的操作の安全性を失うので採らない。
