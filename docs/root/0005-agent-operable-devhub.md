# 0005. エージェントが操作して立ち直れる devhub にする

- **Status**: Accepted (2026-08-05)
- **対象**: リポジトリ全体（internal/httpx / internal/server / internal/docs / internal/reqlog / cmd/devhub / docs）
- **関連**: [root/0002](0002-single-command-slot-and-cli.md)（CLI で見える化する方針の延長）、
  [env-launcher/0002](../env-launcher/0002-cli-env-stop.md)（`/ai-api` の書き込みに手動承認が要ることを前提にしている）
- **参考**: <https://zenn.dev/shunsuke_suzuki/articles/make-cli-ai-friendly>

## Context（背景）

devhub には `/ai-api` というトークン不要のローカル API 面があり、エージェントから
操作されることを最初から想定している。しかし実際に叩かせると、失敗したときに
**次に何をすればいいのかが一切返っていない**ことが分かった。

1. **承認の失敗が区別できない。** `/ai-api` の書き込みはダッシュボード上での承認を待つ。
   拒否されても 60 秒無反応でも、返るのは同じ 403 と
   `{"error":"request rejected or timed out"}` だけだった。拒否なら諦めるべきで、
   タイムアウトなら投げ直すべき —— 正反対の対応が必要なのに、区別する手段がない。
   しかも「ユーザーに承認を頼め」という指示もない。**設計上ほぼ必ず人間のクリックを
   要求する API が、そのことを一言も伝えていなかった。**

2. **エラーが文字列だけ。** `{"error":"<文言>"}` のみで、機械可読な識別子も次の行動もない。
   分岐するには文言を部分一致で見るしかなく、文言を直した瞬間に壊れる。

3. **トークンなしで `/api` を叩いたエージェントが詰む。** 401 が返るだけで、
   トークンはページに埋め込まれるものなのでブラウザ以外は入手できない。
   `/ai-api` という別の入口があることを知る手段がどこにもなかった。

4. **ドキュメントが agent 向けに成立していない。** `docs/` は ADR だけ、つまり
   「なぜそう決めたか」しかない。「どう使うか」「なぜ失敗したか」の文書はゼロ。
   そもそも `docs/` は embed されておらず、バイナリからは読めなかった。

5. **ログが存在しない。** `log.*` の呼び出しは全体で 5 箇所、すべて偶発的なエラー出力。
   特に **always-allow ルールに一致した書き込みは痕跡がゼロ**だった。
   `ShouldAutoApprove` が `Register` の手前で return するため、承認レコードすら作られない。
   一度「常に許可」を押すと、以後その操作は誰にも見えなくなる —— 承認 UI を作り込んだ
   意味が、ルール登録後に消えていた。

## Decision（決定）

### 1. エラーを `{error, code, hint}` にする

`httpx.HTTPError` に `Code`（安定した機械可読 ID）と `Hint`（次に取るべき行動）を足し、
`WriteError` が**設定されているときだけ**出力する。未設定なら従来どおり `{"error": …}`
のまま —— フロントエンド（`shared/net.js` の `apiJson`）は `data.error` しか見ないので無改修。

`code` は API の一部として扱い、改名は破壊的変更とする。`error` は人間向けの文言で、
予告なく変わってよい。

### 2. 承認の失敗を分ける

| 状況 | Status | code |
|---|---|---|
| ユーザーが拒否 | 403 | `approval_rejected` |
| 60 秒無反応 | **408** | `approval_timeout` |

403 のままにしなかったのは、**ステータスだけで分岐できることに意味がある**から。
`code` を読ませる前提にすると、読まない実装が「拒否されたのに再送し続ける」挙動に落ちる。

timeout の hint は「**投げ直してから**ユーザーに承認してもらえ」であって
「今ダッシュボードに出ているものを承認してもらえ」ではない。`Wait` はタイムアウト時に
リクエストを Rejected に落とすので（`approval.go`）、その時点で承認待ち一覧からは
消えている。ここを間違えると、**存在しないプロンプトをユーザーに探させる**ことになる。

### 3. `/api` の 401 は `/ai-api` を名指しする

同じパスの `/ai-api` 版を hint に入れる。ただし `/api/approval/*` だけは例外で、
「`/ai-api` に同等品はない」と返す。承認エンドポイントはトークン必須であり、
**エージェントが自分の要求を自己承認する経路は存在してはならない**。
ここで `/ai-api/approval/…` を案内すると 404 に送るだけでなく、
あってはならない経路の存在を示唆してしまう。

### 4. ドキュメントをバイナリに埋め込み、コマンドにする

`docs/` を `//go:embed` に載せ、`devhub docs list` / `devhub docs show <name>` と
`GET /api/docs` / `GET /api/docs/<name>` から読めるようにする。実装は `internal/docs` 一つで、
CLI と HTTP が同じ `Set` を見る —— hint が名前で案内した文書は、どちらの入口からでも
その名前で見つかる必要があるため。

**トレードオフ**: 文書がバイナリに固定されるので、更新にリリースが要る。
引き換えに、リリース版の devhub が別バージョンの文書を引用することが原理的に起きず、
チェックアウトもネットワークも不要で読める。ローカル開発ツールとしてはこちらを取る。

導線は **help・`version`・エラーの hint・未知サブコマンド**の 4 箇所に張る。
`version` にも置くのは、エージェントが help を読まずにいきなり叩く挙動が
参考記事で実測されているため。人間には 1 行のノイズだが、
気づかれない docs コマンドは無いのと同じ。

### 5. `docs/` に ADR 以外を置く

`docs/agent/` を新設し、`ai-api.md` / `troubleshooting.md` / `cli.md` を置く。
ADR は「なぜそう決めたか」の記録で、**失敗した agent が読むべきものではない**。
`docs/README.md` のレイアウト節にこの区別を明記する。

全ての `docs/*.md` に YAML frontmatter の `description` を必須とし、
テストで強制する（`internal/docs` の `TestEmbeddedDocsAllHaveDescriptions`）。
`docs list` は name と description しか出さないので、description の無い文書は
一覧の中で選びようがない。

### 6. リクエストログは揮発 ring、アーカイブだけ永続

`/api` と `/ai-api` のリクエストを、固定長のメモリ ring（`internal/reqlog`、2000 件）に記録する。
プロセス終了で消える。残したい分だけ明示的に SQLite へコピーする。

- **なぜ揮発か**: 「今なにが起きたか」は devhub が動いている間に訊かれる質問なので、
  それ以上の保持は要らない。ホットパスの disk I/O もゼロになる
- **なぜ ring か**: 無制限に貯めると、放置したプロセスがメモリを食い続ける
- **アーカイブの冪等性**: `UNIQUE(instance, seq)` + `INSERT OR IGNORE`。
  `instance` は起動ごとの乱数 ID、`seq` はその ring 内の連番。
  条件が重なるアーカイブを繰り返しても行は増えない
- **`instance` は ring が持つ**（`reqlog.New(n, instance)`）。`seq` はどの ring も 1 から
  始まるので、`instance` を ring の外（プロセス単位のパッケージ変数など）に置くと、
  ring が 2 つできた瞬間に別々のリクエストが同じキーになる。そのとき
  `INSERT OR IGNORE` は 2 件目を捨て、コントローラはそれを `skipped` として返す ——
  **「アーカイブ済み」と区別がつかない無音の欠落**になる。重複よりこちらが怖いので、
  対にすべき 2 つの値を 1 つのオブジェクトに閉じ込め、`/api/info` の `instance` も
  同じ値を返す（`server.New` が払い出して ring に渡す）
- **記録範囲**: `/api/` と `/ai-api/` のみ。ページ配信とアセットは除外する ——
  数で言えばそちらが大半で、しかも「マシンに何をしたか」を何も語らないので、
  固定長の枠を食い潰すだけになる。ログ自身のエンドポイントも除外（検索が自分の結果を汚す）
- **ボディ**: 既存の `summarizeApprovalBody` をそのまま再利用する。
  password / token / apikey 等は `***` になり 512 rune で切られる。
  **新しい redaction は書かない** —— 承認プロンプトとログで同じ文字列が出ることが、
  片方だけ漏れる事故を防ぐ
- **レスポンス**: 4xx / 5xx のときだけ本文を 256 バイト控える。
  正常系は git diff のような巨大な応答がありうるので保持しない。
  `code` はこの控えた本文から読み戻す（分岐ごとに引き回さないため）

読み取り（`GET /ai-api/logs`）は承認なしで通す。redact 済みで loopback 限定であり、
エージェントが自分の失敗を自己診断できる利点を取る。書き込み（archive / clear）は
他の書き込みと同じく承認を要する —— **エージェントが自分の活動記録を消せてはならない**。
always-allow ルールを作れるのはユーザーだけ（`/api/approval/*` はトークン必須）なので、
この経路が自動化されることはない。

### 7. 承認とログの単位は「パス + クエリ」にする

当初はパスだけを見ていた。これは副作用のある GET に対して壊れていた ——
`GET /ai-api/open?path=X` の「何を開くか」はクエリにしかないので、

- **ログ**には `/api/open` としか残らず、監査対象の唯一の事実が欠けていた
- **承認の detail** も全ての `?path=` で同一文字列になり、
  一度「常に許可」を押すと**任意のディレクトリのオープンが以後無確認**になっていた

クエリを両方に含める。値は body と同じキー名ヒューリスティック（`sanitize.IsSecretKey`）で
伏せ、key 順にソートして正規化する —— 承認ルールが「クライアントがたまたま送った
並び順」に依存してはならないため。

**エスケープは最小限にする。** `url.Values.Encode()` は使わない。この文字列の第一の読者は
「これを許可してよいか」を判断する人間であり、`Encode` は `path=/Users/me/仕事` を
`path=%2FUsers%2Fme%2F%E4%BB%95%E4%BA%8B` にしてしまう —— 承認プロンプトで読めず、
ログのフリーテキスト検索（保存文字列への部分一致）にも当たらない。
必要なのは URL 安全性ではなく**単射性**だけで、この文字列は誰も再パースしない。
エスケープするのは `%` `&` `=` `?`・空白・ASCII 制御文字に限る。

空白を含めるのは可読性のためではない。detail は `detailMatchesPattern` が
**スペースを境界として**前方一致で照合するので、値の中に空白を通すと
「ユーザーが見ていないリクエストを 1 つの always-allow が覆う」境界を
値の側から捏造できてしまう。`?` も同じ理由 —— パスとクエリを `?` で連結するので、
パスに `?` が入ると送られていないクエリを偽装できる。

**エスケープはクエリだけでなくパスにもかける。** `r.URL.Path` は
パーセントデコード済みなので、`/ai-api/x%20y` はここに空白入りで届く ——
クエリ側でわざわざ潰した、まさにその文字。現状これがハンドラに届かないのは
gateway のルート照合（完全一致 or 前置）がそういうパスに当たらないからだが、
それは gateway の性質であってこの文字列の性質ではない。両方に掛ければ、
将来 gateway が変わっても前提が崩れない。

**バイト単位で回す。** rune で回すと不正 UTF-8 の各バイトが U+FFFD になるので、
`?a=%FF` と `?a=%FE` が同じラベルに潰れ、片方への always-allow がもう片方を覆う。
正しい UTF-8 はバイト列がそのまま通るので可読性は変わらない。
引き換えに C1 制御文字（U+0085 等）は素通りするが、区切りではないので境界は作れない。

副作用として「常に許可」の粒度が細かくなる。`?path=/a` を許可しても `?path=/b` は
再確認される。これは劣化ではなく、元の粒度が広すぎたということ。

なお「既存ルールがクエリ付きリクエストを覆わない」ことは 2 つの別々の理由で成立していて、
壊れ方が違うので両方テストで固定してある（`TestARuleDoesNotReachAcrossAQueryString`）:

1. 旧形式のルール（`GET /ai-api/open (no request body)`）は、パス直後が `(` と `?` で
   食い違うので、そもそも前方一致にならない
2. クエリの途中で終わるパターン（`?path=/a`）は前方一致してしまうので、
   **スペース境界アンカーだけ**が `?path=/abc` への波及を止めている

ログのパスは `/ai-api` 接頭辞を落として `/api/...` に正規化する。入口は surface 列が
既に区別しているので、正規化しないと `path=/api/git` の絞り込みが
**エージェントのリクエストだけを取りこぼす** —— このログが見せたい相手そのものを。

**クエリ値はキー名（`sanitize.IsSecretKey`）でしか伏せられない。** 当たらなかった値は
そのままログに入り、アーカイブでディスクに落ちる。これは決定 #9（非 JSON ボディ）と
逆向きの判断で、意図的にそうしている —— 監査したい事実はクエリ値そのものなので、
「redaction が効かないかもしれないから出さない」を選ぶと、この決定の目的が消える。
成立の条件は「秘密をクエリで受けるルートが無い」こと。現状クエリを取るのは
`path` / `n` / `file` / `staged` / `suggest` / `source` とフィルタ系だけで、どれも秘密ではない。
**秘密をクエリ引数で受けるルートを足すときは、ここを見直すこと。**

### 8. ログを消す経路は `/ai-api` から塞ぐ

`POST /ai-api/logs/clear` と `/ai-api/logs/archive` は 403 `no_ai_api_route` で拒否する。
読み取り（`GET /ai-api/logs`）は通したままにする。

承認を挟むだけでは足りない。**承認は「常に許可」1 回で自動になり、
その規則を作った記録自体が消去対象に含まれる**。監視対象が監視記録を、
無記録で、自分の判断で消せる状態は、ログを置く前提を崩す。

あわせて `/api/logs/clear` と `/api/logs/archive` は記録対象に含めた（読み取りは除外のまま）。
`ServeHTTP` はハンドラが返った**後**にエントリを足すので、live の消去はそれ自身の記録を
生き残らせる —— 消去後の ring には「誰がいつ消したか」の 1 行だけが残る。
これが無いと、消去は「何も起きなかった時間」と区別がつかない。

**この決定が塞いでいない穴が 2 つある。どちらも意図して残す。**

**`POST /ai-api/restart`（および `/rebuild`・`/update/apply`）** — 上の論法がそのまま
当てはまる。承認ゲートには乗るが、そこはこの決定が「不十分」と断じた場所であり、
always-allow を 1 つ持ったエージェントは無記録で ring を空にできる。しかも `clear` より悪い:
`clear` は自分自身の記録を残すが、restart はプロセスごと入れ替わるので**その 1 行も残らない**。
それでも封鎖しないのは、restart がログ消去を目的とする操作ではなく、
エージェントが devhub を運用するうえで正当に必要だからで、封鎖すれば
「揮発ログを守るために、ログが記録したい作業そのものを止める」ことになる。
代償は明示しておく —— **restart をまたぐと live ring は失われ、それ自体も記録に残らない。
残したいものは事前にアーカイブする以外にない。**

**`POST /api/logs/clear?source=archive`** — 永続側の行を消す操作で、その記録は
揮発 ring にしか入らない。つまり**再起動をまたぐと archive の消去も「静かな時間」と
区別がつかなくなる**。上の「消去はそれ自身の記録を生き残らせる」は live についてのみ真。
`/ai-api` からは封鎖済みなのでエージェント経路ではなく、ユーザーが自分の判断で
自分の記録を消す操作なので、監査対象として扱っていない。

**`POST /ai-api/db/delete` を devhub 自身のストアに向ける経路** — db ツールは
リクエストが渡した `path` の SQLite を rw で開くので、devhub のストアを指せば
`request_log_archive` の行に届く。上の 2 つより狭い（承認 detail にボディ要約が入るので
always-allow は接続先とテーブルごとに固有になる）が、届く先が**揮発 ring ではなく
archive** である点はより悪い。封鎖しないのは、任意のローカル DB を開けることが
db ツールの機能そのもので、自分のストアだけを除外する特別扱いは、
「devhub のストアがどこにあるか」を db ツールに教えることになるため。
**この 3 つは、決定 #8 が守っているのは「ログを消すための API」だけであって
「ログが消えないこと」ではない、という限界の別々の現れ方である。**

### 9. JSON でないボディは中身を記録しない

`summarizeApprovalBody` の redaction はキー名ヒューリスティックなので、
JSON でないボディには**一切かからない**。承認プロンプトに一瞬出るだけなら許容できたが、
同じ文字列がログに入り、アーカイブでディスクに落ちるようになった時点で許容できない。
`(non-JSON body, N bytes)` に潰す。devhub の書き込みは全て JSON なので、
この分岐に来る時点で「壊れているか想定外」であり、形だけ分かれば足りる。

## Consequences（結果）

- エラーの `code` は API 契約になった。改名には移行手順が要る
- 承認タイムアウトの HTTP ステータスが 403 → 408 に変わった。
  `/ai-api` を叩く既存クライアントがあれば影響する（devhub 自身のフロントエンドは
  `/ai-api` を使わないので UI への影響はない）
- 文書の更新にリリースが必要になった
- `tools.Registry` の引数が増えた（store, docs, ring）。
  合成ルートは 1 箇所なので呼び出し側の変更は `server.New` のみ
- **always-allow を押した後の操作が見えるようになった。** これが一連の変更で
  一番実効性のある差分で、`/logs` を開いて `approval=auto` で絞ると出る
- **既存の always-allow ルールのうち、クエリ付きリクエストに対するものは効かなくなった**
  （#7）。実質 `GET /ai-api/open` のみで、そこは意図的に再確認させたいケース。
  ただし**効かなくなったルールは `GET /api/approval/rules` の一覧にそのまま残り、
  UI にも何の印も出ない** —— 「登録したのに毎回聞かれる」ように見える。
  対象が 1 ルールなので放置するが、ルールの一覧が「今も効いているもの」を
  意味しなくなったこと自体は残しておく
- ログの `path` は `/api/...` に正規化されたので、`/ai-api/...` で絞る検索は当たらない。
  入口を絞るなら surface 列を使う。
  **ただしこの変更より前にアーカイブされた行は `/ai-api/...` のまま残っている** ——
  `path=/ai-api/git` は「何も返らない」ではなく「古い行だけが返る」という、
  一番紛らわしい状態になる

## Alternatives considered（検討した代替案）

- **ログを最初から SQLite に書き、起動時に未アーカイブ行を DELETE する。**
  検索が SQL でそのまま書け、live と archive のコード経路が一本化される。
  採らなかったのは、リクエストのたびに disk へ書くことになるため。
  ローカル用途なら実測上は問題ない量だが、「ログのために本来の処理を遅くしない」
  ほうが性質として素直だと判断した。引き換えに live と archive で
  フィルタ実装が二重になっている（`reqlog.Filter` と `storage.RequestLogFilter`）
- **`hint` を全エラーに機械的に付ける。** 付ける先を「詰まりやすい経路」に絞った。
  意味のない hint が並ぶと、hint 全体が読み飛ばされるようになる
