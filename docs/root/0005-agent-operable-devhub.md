# 0005. エージェントが操作して立ち直れる devhub にする

- **Status**: Accepted (2026-08-05)
- **対象**: internal/httpx / internal/server
- **関連**: [root/0002](0002-single-command-slot-and-cli.md)（CLI で見える化する方針の延長）、
  [env-launcher/0002](../env-launcher/0002-cli-env-stop.md)（`/ai-api` の書き込みに手動承認が要ることを前提にしている）
- **参考**: <https://zenn.dev/shunsuke_suzuki/articles/make-cli-ai-friendly>

## Context（背景）

devhub には `/ai-api` というトークン不要のローカル API 面があり、エージェントから
操作されることを最初から想定している。しかし実際に叩かせると、失敗したときに
**次に何をすればいいのかが一切返っていない**ことが分かった。

1. **承認の失敗が区別できない。** `/ai-api` の書き込みはダッシュボード上での承認を待つ。
   拒否されても 60 秒無反応でも、返るのは同じ 403 と
   `{"error":"request rejected or timed out"}` だけだった。拒否なら諦めるべきで、
   タイムアウトなら投げ直すべき —— 正反対の対応が必要なのに、区別する手段がない。
   しかも「ユーザーに承認を頼め」という指示もない。**設計上ほぼ必ず人間のクリックを
   要求する API が、そのことを一言も伝えていなかった。**

2. **エラーが文字列だけ。** `{"error":"<文言>"}` のみで、機械可読な識別子も次の行動もない。
   分岐するには文言を部分一致で見るしかなく、文言を直した瞬間に壊れる。

3. **トークンなしで `/api` を叩いたエージェントが詰む。** 401 が返るだけで、
   トークンはページに埋め込まれるものなのでブラウザ以外は入手できない。
   `/ai-api` という別の入口があることを知る手段がどこにもなかった。

## Decision（決定）

### 1. エラーを `{error, code, hint}` にする

`httpx.HTTPError` に `Code`（安定した機械可読 ID）と `Hint`（次に取るべき行動）を足し、
`WriteError` が**設定されているときだけ**出力する。未設定なら従来どおり `{"error": …}`
のまま —— フロントエンド（`shared/net.js` の `apiJson`）は `data.error` しか見ないので無改修。

`code` は API の一部として扱い、改名は破壊的変更とする。`error` は人間向けの文言で、
予告なく変わってよい。

### 2. 承認の失敗を分ける

| 状況 | Status | code |
|---|---|---|
| ユーザーが拒否 | 403 | `approval_rejected` |
| 60 秒無反応 | **408** | `approval_timeout` |

403 のままにしなかったのは、**ステータスだけで分岐できることに意味がある**から。
`code` を読ませる前提にすると、読まない実装が「拒否されたのに再送し続ける」挙動に落ちる。

timeout の hint は「**投げ直してから**ユーザーに承認してもらえ」であって
「今ダッシュボードに出ているものを承認してもらえ」ではない。`Wait` はタイムアウト時に
リクエストを Rejected に落とすので（`approval.go`）、その時点で承認待ち一覧からは
消えている。ここを間違えると、**存在しないプロンプトをユーザーに探させる**ことになる。

### 3. `/api` の 401 は `/ai-api` を名指しする

同じパスの `/ai-api` 版を hint に入れる。ただし `/api/approval/*` だけは例外で、
「`/ai-api` に同等品はない」と返す。承認エンドポイントはトークン必須であり、
**エージェントが自分の要求を自己承認する経路は存在してはならない**。
ここで `/ai-api/approval/…` を案内すると 404 に送るだけでなく、
あってはならない経路の存在を示唆してしまう。

## Consequences（結果）

- エラーの `code` は API 契約になった。改名には移行手順が要る
- 承認タイムアウトの HTTP ステータスが 403 → 408 に変わった。
  `/ai-api` を叩く既存クライアントがあれば影響する（devhub 自身のフロントエンドは
  `/ai-api` を使わないので UI への影響はない）

## Alternatives considered（検討した代替案）

- **`hint` を全エラーに機械的に付ける。** 付ける先を「詰まりやすい経路」に絞った。
  意味のない hint が並ぶと、hint 全体が読み飛ばされるようになる
- **承認タイムアウトの 60 秒を延ばす。** 伝え方の問題であって長さの問題ではない、と整理した。
  正しく「ユーザーに頼んでから投げ直せ」と言えれば、待ち時間は短いほうがよい
